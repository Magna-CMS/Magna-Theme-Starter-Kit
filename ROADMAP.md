# The plan for Magna theme developers

Magna has a Plugin SDK for people who extend it with code. Themes needed their own front door.
A theme for Magna Pages is not code, so its developers need a different kind of help: a clear
contract, a reference to copy, fast feedback, and a path to publishing. This kit is that front
door. This document says what it already does, what comes next, and what should change in Magna
itself.

## Who this is for

| Person | Arrives with | Needs |
|---|---|---|
| **Designer / front-end developer** | HTML, CSS, a little templating | To know what the platform gives them, and where their CSS goes. No PHP knowledge assumed. |
| **Agency developer** | A client brand and a deadline | A working base to copy, and confidence it passes review. |
| **Plugin author** | A plugin whose blocks must look native | The addon model ([chapter 9](docs/09-addons.md)). |
| **Store seller** | A finished theme | Packaging, versioning and the rules the store checks. |

## Principles

1. **Learn from a working theme, not a spec.** Every rule in the guide points at a line of the
   Starter theme that follows it.
2. **Fast feedback without a server.** `theme-lint` runs in under a second, with only PHP
   installed. Nobody should discover a rule from a store rejection.
3. **Never drift from the platform.** The block reference and the lint tool's block data are
   generated from Magna's own source. The lint tool's rules are a line-for-line mirror of
   `magna:theme:check`, and every documented behaviour was checked against a running site.
4. **Tokens first, CSS second, overrides last.** The guide's order is the order of a theme's
   longevity: tokens survive every platform change, CSS survives most, overrides need care.

## Phase 1 — Foundation (this release, v1.0)

- [x] **Starter theme**: complete, commented, verified clean by `magna:theme:check` and rendered
      on a real Magna 1.7.0 / Magna Pages 0.6.0-alpha site (light, dark, mobile, builder mode)
- [x] **Developer guide**: 13 chapters, from the mental model to publishing
- [x] **Block reference**: every block's fields, classes, resolved data and behaviour hooks,
      generated by `tools/sync-blocks.php`
- [x] **`theme-lint`**: the platform's audit rules plus kit checks for layout contract, page-cache
      safety, override shape, tokens, manifest and demo content
- [x] **`new-theme`**: copy and re-prefix Starter under your own name
- [x] **`package`**: lint-gated zip in the layout Magna's installer expects
- [x] **JSON Schemas**: `theme.json`, `tokens.json`, site kits, for editor autocomplete and CI
- [x] **CI**: lint, scaffold, package and schema checks on every push; a scheduled job that fails
      when Magna's block library drifts from the reference

## Phase 2 — Depth (next)

- [ ] **More reference themes**, each teaching one thing Starter deliberately leaves out:
  - an *editorial* theme (web fonts, rich text and Magna Blog styling; see Eva)
  - a *landing-page* theme (patterns as the main product, `blockSeeds` everywhere)
  - an *addon* example, styling a plugin's blocks in Starter
- [ ] **Recipes** chapter: sticky header, mega-menu from nested menus, a drawer via `$menu()`,

- [ ] **Theme README template**: band classes and token roles, which editors need
- [ ] **Pre-commit hook** sample running `theme-lint`

## Phase 3 — Platform proposals (for Magna core and Magna Pages)

Each of these removes a sharp edge the guide currently has to explain. They are proposals, not
commitments, and each needs the platform maintainers.

| Proposal | Why |
|---|---|
| **`magna:theme:make`** in core, scaffolding from this kit's Starter | One command, discoverable from `php artisan list`, the way `magna:plugin:make` is for plugins |
| **Section class vocabulary in `theme.json`** (e.g. `"sectionClasses": {"starter-band--muted": "Muted band"}`) shown as a picker in the builder | Today band classes are free text that editors must learn from a README; the Pages README lists this as a known gap |
| **Token `label` and grouping in the Design panel** | `label` is already in `tokens.json`; the panel lists raw variable names |
| **A block gallery page** in the builder: every block with sample data, in the active theme | The fastest possible styling loop; today it is a scratch page built by hand |
| **Versioned layout payload** (a documented `layoutContract` version) | Lets a theme declare which layout variables it relies on, the way `compat.plugins` does for features |
| **Theme asset serving** (a small, cache-busted `assets/` route) | Removes the need to inline everything; lets themes ship fonts and images |
| **Resolved media in block payloads** | Media-backed blocks fetch inside their views; moving that to resolvers would make every block safely overridable |
| **A public theme section in the Plugin SDK docs** linking here | One documentation entry point for everyone extending Magna |

## How we'll know it works

- A designer with no Magna experience goes from clone to their own palette on a running site in
  **under 30 minutes** (the quick start's promise).
- Store submissions **pass `magna:theme:check` on the first attempt**, because `theme-lint` caught
  everything first.
- The docs **never go stale**: the scheduled drift job fails the week the platform changes, and
  the fix is a regenerated reference.
- Issues tagged *docs-gap* trend to zero.
